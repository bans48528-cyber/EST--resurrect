# EST 最小可升级 APP

目标芯片：`STM32F429ZGT6`。本工程只实现原 EST USB HID、心跳和固件升级接收，不改板内 Bootloader。

## 已实现

- APP 链接地址固定为 `0x08010000`，Update 区从 `0x08080000` 开始。
- 上电第一时间把 `PE2/PB_CON` 配为高电平输出，保持板卡电源；该电平与 EST 3.0 官方 Bootloader/APP 的 `Power_On()` 一致。
- APP 入口用约 2 秒红蓝交替作为启动签名；正常运行后红灯熄灭、蓝灯以 500 ms 周期切换，便于区分 Bootloader、APP 入口和 APP 主循环。
- 清除 Bootloader 遗留中断和主要外设状态，使用 8 MHz HSE 建立 168 MHz/48 MHz USB 时钟。
- USB HID 使用 EST 3.0 官方链路：`OTG HS + USB3300 ULPI`，复现 `0483:5750`、HS 产品字符串/序列号、1024 字节端点和 35 字节 Report Descriptor。
- 支持旧心跳命令，六字节版本由构建参数 `APP_VERSION` 指定。
- 六个面板按键支持 25 ms 消抖和只读诊断查询，不改变原升级协议。
- 外部 Flash 使用原理图确认的 `PA15 + PC10/PC11/PC12` 接线，支持 JEDEC ID、保护状态、4 字节模式和安全测试区诊断。`flash-test` 仅在确认最后一个 4 KiB 扇区为空时临时写入 32 字节，核对高地址和低地址别名后立即擦除并恢复 3 字节模式。
- 使用当前实物验证过的 `PD14/PG2/PD15` 驱动 UC1638 LCD，启动后清除 Bootloader 遗留画面并显示当前版本号。不要把 `PB13` 用作 LCD 时钟，它属于当前高速 USB 链路。
- 输出 A 口沿用旧固件的 `PB9/TIM4_CH4 + PG10/PG11` 接线。上电默认强制停转，只有收到 `motor-test` 命令才以 30% 功率依次正转 700 ms、停止 400 ms、反转 700 ms 并再次停止；升级开始、关机和主机停止命令都会强制停转。
- 输出 A 口测速沿用旧固件的 `PE5/TACHOA0 + PE6/TACHOA1` 接线。`PE5` 双边沿触发计数，结合 `PE6` 判断方向；`motor-tacho-test` 会分别返回正转、反转和总计数。
- 输出 B 口沿用旧固件和 V5 原理图共同确认的 `PB8/TIM4_CH3 + PD0/PD1` 控制线及 `PE13/PE14` 测速线。`motor-tacho-test --port B` 只驱动 B 口。
- 输出 C 口使用当前 V5 原理图确认的 `PD13/TIM4_CH2 + PG12/PG13` 控制线及 `PC7/PC6` 测速线。`motor-tacho-test --port C` 只驱动 C 口；启动、升级、关机及异常停止会同时关闭 A、B、C 三口。
- 输出 D 口使用当前 V5 原理图确认的 `PD12/TIM4_CH1 + PA10/PA9` 控制线及 `PC9/PC8` 测速线。`motor-tacho-test --port D` 只驱动 D 口；加入 D 口后所有安全停止路径会同时关闭 A、B、C、D 四口。
- `motor-dual-test` 以默认 30% 功率让 A、B 同时正转、同时主动刹车、同时反转、再次主动刹车并关闭，分别返回两路正反转测速计数及速度接近程度。该命令用于验证两路 TIM4 PWM 和两组编码器可同时工作。
- `M0.43A` 新增通用马达控制命令 `0x17`，把诊断流程之外的 A-D 端口选择、有符号功率、自由滑行、主动刹车、测速读取和计数清零统一为可供新上位机调用的接口。各端口可同时保持不同方向和功率，旧升级协议、帧格式、ACK 和 `0x13-0x16` 诊断命令保持不变。
- 通用马达控制不使用固件自动超时或定时续约；输出保持到上位机明确改变状态。升级开始、最终关机和旧诊断停止路径仍调用 `board_motor_stop()` 关闭 A-D 全部输出。
- `motor-tacho-test` 支持 1%-100% 可调功率。80% 及以上使用短测试时序：正转 500 ms、关闭驱动 800 ms、反转 500 ms、再次关闭驱动，以降低高速直接换向的冲击。
- `motor-stop-compare` 以默认 60% 功率分别测试旧固件留下的两种合法停车电平组合，通过停车后继续产生的测速脉冲量，实机辨认自由滑行和主动刹车。每项只驱动 600 ms、测量 1500 ms，结束和异常退出均恢复到已经验证过的低电平开漏停止状态。
- 按 1024 字节 HID report 接收升级逻辑帧，同时允许协议层分片输入；逐帧校验、连续性检查、重复上一帧 ACK 和 400 秒会话超时。
- 半帧中断后，如果主机停顿并从新帧头重发，接收器会自动丢弃残帧；设备回包使用 4 项 FIFO，避免前一 ACK 尚在 USB 总线上时丢掉重发响应。
- 首帧确认 `APP=` 后擦除 Sector 8-11，写入完成后检查 MSP 和 Thumb Reset_Handler。
- 最后擦除 Sector 3，按旧语义写入 `package_length - 1`，最后写升级状态 `0x0000`；最终 ACK 发出后拉低 `PE2/PB_CON` 关机，等待人工重新开机。这与 EST 3.0 官方 APP 行为一致，不使用未经验证的软件复位路径。
- 打包器把最终升级文件填充为固定 256 KiB，满足旧 Bootloader 的长度限制。
- 每次构建自动检查 APP 地址、向量表、入口第一条关中断指令、USB VID/PID、1024 字节端点、HS HID/Qualifier 描述符、产品字符串、版本文本、`APP=` 包头、填充内容和 SHA-256 清单。
- `make test` 还会读取 V5.0 当前引脚表，检查电源、LED、六个按键、LCD、外部 Flash 和 USB 的代码接线，并拒绝任何重复占用或与原理图不一致的修改。

## 构建

工程内已固定包含 libopencm3 commit `2da12dc96e0b9e42a3332348dd9b02a0a17981f8`。Windows 当前机器可执行：

```powershell
$env:PATH='D:\AIMODU~1\AI_MOD~1\ARM_GC~1\bin;E:\Git\usr\bin;' + $env:PATH
& 'D:\AIMODU~1\AI_MOD~1\make.exe' -j4 all
```

生成 v1/v2 自升级验收包：

```powershell
& 'D:\AIMODU~1\AI_MOD~1\make.exe' -j4 verification-pair
```

`all` 和 `verification-pair` 都会自动执行产物检查。也可以单独执行 `make verify` 复查当前构建目录。

主要产物：

| 文件 | 用途 |
| --- | --- |
| `build/est_minimal_upgrade_app.bin` | 原始 APP，仅供调试器写到 `0x08010000` |
| `build/est_minimal_upgrade_app.app.bin` | `APP=` + 原始 APP，未填充参考包 |
| `build/est_minimal_upgrade_app.upgrade.bin` | 256 KiB，交给旧上位机升级工具 |
| `build/est_minimal_upgrade_app.manifest.json` | 地址、长度和 SHA-256 检查信息 |

不要把原始 `.bin` 交给旧升级工具；应选择 `.upgrade.bin`。该文件已经带 `APP=`，如果旧工具仍会自动添加文件头，需要先确认它的 `Firmware_check()` 不会重复添加。原工具识别到已有 `APP=` 时不会再添加。

## 实机验收顺序

1. 按住第一个按键开机，让板卡进入 Bootloader 下载界面；当前实物表现为红灯闪烁，心跳为 `03.00B`。
2. 使用 `tools/est_hid_sender/est_hid_sender.py` 发送 `.upgrade.bin`。
3. 确认传输完成、Bootloader 搬运后红/蓝诊断灯交替闪烁。
4. 确认 Windows 重新枚举 `VID_0483&PID_5750`，HID 输入/输出报告长度为 `1025`。
5. 确认心跳返回当前六字节构建版本。
6. 生成仅改变版本号的下一版并从最小 APP 再升级一次，验证完整闭环。

只有第 6 步完成，才能说明“新 APP 接收升级包 -> 原 Bootloader 搬运 -> 新 APP 再启动”的闭环真正成立。当前源码和本机测试不能替代实机验证。

当前实物的 Bootloader 在搬运进度达到 `100%` 后不会自动清屏或重新开机；灯熄灭后需要人工断电重启。M0.40A 的屏幕版本显示、蓝灯闪烁和 USB 心跳均正常。M0.39A 在正常开机状态直接接收 M0.40A 的 260 帧，最终 ACK 后约 1 秒内自动关机，确认日常升级不需要预先进入旧引导；只有直接把包发给旧引导时才不会经过 APP 自动关机流程。A 口 30% 测速实测为 `+165/-168`，100% 为 `+421/-375`；A 口自由滑行/主动刹车为 `296/39`。B 口 30% 测速为 `+163/-168`，自由滑行/主动刹车为 `323/37`。M0.38A 的 A/B 同步测试为 A `+162/-172`、B `+178/-178`，实物确认两口同时动作并停止。M0.39A 的 C 口中型马达两次 30% 测速约为 `+108/-303`、`+110/-322`，肉眼正反转速度相同；把同一马达换到已验证 A 口后仍为 `+134/-293`，因此该不对称来自马达个体或中型马达编码器特性，而不是 C 口接线。M0.40A 的 D 口首次测试仅 `+3/0`，重新确认插接后连续两次为 `+143/-246`、`+156/-243`，肉眼确认两个方向均动作并正常停止，因此 D 口驱动和测速已通过。当前设备运行 `M0.43A`：通用控制下 A 口 `+30/-30` 为 `+244/-258`，D 口 `+30/-30` 为 `+215/-369`；A `+30` 与 D `-30` 同时运行时分别为 `+246/-437`。D 口 80% 停车对比为自由滑行后续 `136`、主动刹车后续 `13`，差异明确。此前 `M0.31A` 的 W25Q256 高地址临时写入、读回、擦除及模式恢复也已验证成功。
