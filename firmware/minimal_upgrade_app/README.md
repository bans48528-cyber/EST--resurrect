# EST 最小可升级 APP

目标芯片：`STM32F429ZGT6`。本工程只实现原 EST USB HID、心跳和固件升级接收，不改板内 Bootloader。

## 已实现

- APP 链接地址固定为 `0x08010000`，Update 区从 `0x08080000` 开始。
- 上电第一时间把 `PE2/PB_CON` 配为高电平输出，保持板卡电源；该电平与 EST 3.0 官方 Bootloader/APP 的 `Power_On()` 一致。
- APP 入口用约 2 秒红蓝交替作为启动签名；正常运行后红灯熄灭、蓝灯以 500 ms 周期切换，便于区分 Bootloader、APP 入口和 APP 主循环。
- 清除 Bootloader 遗留中断和主要外设状态，使用 8 MHz HSE 建立 168 MHz/48 MHz USB 时钟。
- USB HID 使用 EST 3.0 官方链路：`OTG HS + USB3300 ULPI`，复现 `0483:5750`、HS 产品字符串/序列号、1024 字节端点和 35 字节 Report Descriptor。
- 支持旧心跳命令，六字节版本由构建参数 `APP_VERSION` 指定。
- 六个面板按键支持 25 ms 消抖和只读诊断查询，不改变原升级协议。
- 外部 Flash 使用原理图确认的 `PA15 + PC10/PC11/PC12` 接线，支持 JEDEC ID、保护状态、4 字节模式和安全测试区诊断。`flash-test` 仅在确认最后一个 4 KiB 扇区为空时临时写入 32 字节，核对高地址和低地址别名后立即擦除并恢复 3 字节模式。
- 使用当前实物验证过的 `PD14/PG2/PD15` 驱动 UC1638 LCD，启动后清除 Bootloader 遗留画面并显示当前版本号。不要把 `PB13` 用作 LCD 时钟，它属于当前高速 USB 链路。
- 输出 A 口沿用旧固件的 `PB9/TIM4_CH4 + PG10/PG11` 接线。上电默认强制停转，只有收到 `motor-test` 命令才以 30% 功率依次正转 700 ms、停止 400 ms、反转 700 ms 并再次停止；升级开始、关机和主机停止命令都会强制停转。
- 输出 A 口测速沿用旧固件的 `PE5/TACHOA0 + PE6/TACHOA1` 接线。`PE5` 双边沿触发计数，结合 `PE6` 判断方向；`motor-tacho-test` 会分别返回正转、反转和总计数。
- 输出 B 口沿用旧固件和 V5 原理图共同确认的 `PB8/TIM4_CH3 + PD0/PD1` 控制线及 `PE13/PE14` 测速线。`motor-tacho-test --port B` 只驱动 B 口。
- 输出 C 口使用当前 V5 原理图确认的 `PD13/TIM4_CH2 + PG12/PG13` 控制线及 `PC7/PC6` 测速线。`motor-tacho-test --port C` 只驱动 C 口；启动、升级、关机及异常停止会同时关闭 A、B、C 三口。
- 输出 D 口使用当前 V5 原理图确认的 `PD12/TIM4_CH1 + PA10/PA9` 控制线及 `PC9/PC8` 测速线。`motor-tacho-test --port D` 只驱动 D 口；加入 D 口后所有安全停止路径会同时关闭 A、B、C、D 四口。
- `motor-dual-test` 以默认 30% 功率让 A、B 同时正转、同时主动刹车、同时反转、再次主动刹车并关闭，分别返回两路正反转测速计数及速度接近程度。该命令用于验证两路 TIM4 PWM 和两组编码器可同时工作。
- `M0.43A` 新增通用马达控制命令 `0x17`，把诊断流程之外的 A-D 端口选择、有符号功率、自由滑行、主动刹车、测速读取和计数清零统一为可供新上位机调用的接口。各端口可同时保持不同方向和功率，旧升级协议、帧格式、ACK 和 `0x13-0x16` 诊断命令保持不变。
- 通用马达控制不使用固件自动超时或定时续约；输出保持到上位机明确改变状态。升级开始、最终关机和旧诊断停止路径仍调用 `board_motor_stop()` 关闭 A-D 全部输出。
- `M0.44A` 新增 1 号输入口颜色/灰度传感器驱动和通用输入命令 `0x18`。驱动使用 V5 原理图确认的 `PF4/PF5/PF6/PF7 + PB3/PB4 + PA0/PA1/UART4 + PG15`，兼容 EST/EV3 UART 传感器的 2400 波特率握手、传感器类型 `0x1D`、57600 波特率数据通信，以及反射光、环境光和颜色三种模式。升级开始和关机时会关闭该输入口。
- `M0.45A` 在 LCD 上实时显示 1 号输入口的模式和读数：反射灰度与环境光显示数字，颜色模式显示颜色名称；按下任意面板按键即可循环切换三种模式。UART4 接收改为中断缓冲，避免 LCD 刷新期间漏掉传感器数据。
- `M0.46A` 将同一套 EST/EV3 UART 传感器驱动扩展到 1-4 号输入口，每个口使用独立串口、供电控制和接收缓冲。LCD 同时显示四个口的连接状态或实时读数，任意按键会让四口一起切换反射灰度、环境光和颜色模式；`0x18` 命令可分别读取、切换或重启任一输入口。
- `M0.47A` 增加无芯片的 EST/EV3 触碰传感器。沿用旧主机的电阻识别和按键电压门限，自动区分 UART 颜色传感器与触碰传感器；LCD 对触碰传感器实时显示 `UP`（松开）或 `DOWN`（按下），四个输入口均可使用。
- `M0.48A` 增加类型 `0x1E` 的 EST/EV3 超声波传感器。继续使用现有 UART 握手和模式选择协议；LCD 模式 0 显示带一位小数的厘米距离，模式 1 显示英寸距离，模式 2 显示是否探测到物体。四个输入口共用同一实现，颜色和触碰传感器逻辑保持不变。
- `M0.49A` 增加类型 `0x06` 的 EST 温度传感器。严格沿用旧产品的 `0x4C` I²C 地址、`0x01/0x60` 识别流程和 `0x00` 温度寄存器；四个输入口均可自动识别，LCD 默认实时显示带一位小数的摄氏温度，按任意面板按键可切换华氏温度，并支持零下温度的负号显示。
- `M0.50A` 将温度传感器 I²C 的每个高、低电平保持时间恢复为旧固件的约 50 微秒。M0.49A 实物上能够看见 2 号口接入后的电气变化，但较快的首版通信未得到老式 8051 传感器模块应答。
- `M0.51A` 继续复刻旧固件的 I²C 端口选择：先根据 pin 1 未加载、pin 6 高电平识别 I²C 候选模块，再将该端口的 `RXIN_EN` 从 UART 使用的低电平切换为高电平，等待 20 毫秒后才进行握手；断开、重启或关机时恢复低电平。实物已确认温度传感器能够自动识别并正常显示温度。
- `M0.52A` 建立新上位机 USB 应用协议 `1.0` 的第一个整机快照命令 `0x19`。一次只读请求可返回固件版本、功能列表、开机时间、电量、六个按键、A-D 马达状态和 1-4 号输入口状态；电池使用 V5 原理图确认的 `PF3 / ADC3 channel 9`，旧 `0x05` 升级和已有控制命令均保持不变。
- `M0.53A` 将 LCD 改为左右两栏实时总览：左侧显示 1-4 号输入口，右侧同时显示 A-D 马达累计计数。新增 `PA8/TIM1_CH1` 背光 PWM，开机依次执行全亮、20% 亮度、熄灭、恢复全亮；新增板载 VS 音频芯片测试，使用 V5 引脚表确认的 `PG4/PG5/PG6/PG7`，播放两段内建正弦测试音。音频操作期间临时把共享 SPI3 切到旧音频芯片所需模式，完成每次传输后恢复外部 Flash 使用的 SPI 模式。
- `M0.54A` 在 LCD 底部持续显示电池百分比及音频测试状态；把开机声音改为最大测试音量、三段不同音高、每段 0.8 秒，并继续保留 M0.53A 的背光、输入口和马达计数显示。
- `M0.55A` 不再使用 VS 芯片的内部正弦测试模式，改为生成标准 8 kHz、8 位、单声道 PCM WAV 数据并通过 SDI 数据通道发送。实物声音明显增大，但播放时间很短，未通过完整播放验收。
- `M0.56A` 将 WAV 测试数据从约 1.6 秒延长到约 5 秒并加入五段音符；实物确认播放过程仍不正常。音频输出暂缓处理，本版本保留用于问题追溯，不能作为音频已通过的依据。
- `M0.57A-M0.61A` 依次完成 MPU6050 陀螺仪、NXT 模拟声音、EST/EV3 红外传感器和大型/中型马达类型稳定识别；实机结果及异常版本统一记录在 `firmware/releases/README.md`。
- `M0.62A` 新增类型感知的马达转速估算和 `0x1B` 单口角度/圈数控制。大型和中型马达分别使用官方测速基准、采样窗口、短行程限速及减速角；控制支持到位刹车、恢复自由滑行和超时保护。
- `M0.63A` 把每路马达的有符号圈速百分比、累计角度和累计圈数同时显示在 LCD，分别标记为 `S`、`A` 和 `R`，便于不依赖电脑端直接进行实机验收。
- `M0.64A` 修正 M0.63A 的 LCD 宽度估算错误：马达栏左移到 `x=72`，用最多 18 字符的紧凑格式完整显示类型、转速、角度和圈数，并通过编译期检查保证不超过 180 像素屏幕边界。
- `M0.65A` 增加马达类型静止刷新和持续闭环定速。定速控制复用大型/中型马达的官方测速参数和 10 ms 增量比例控制，支持有符号目标以及自由滑行、主动刹车两种明确停止方式；首版静止刷新使用 H 桥零差分电平，实机只能识别当前恰好落入有效电压窗的马达，不能解决大型马达编码器相位歧义。
- `M0.66A` 尝试在 A-D 四路均停止时把目标口编码器 pin 6 依次驱动为高、低并分别读取 pin 5 ADC。实机确认 H 桥全程关闭且马达不转，但 B 口大型马达仍返回 `unknown / 129 mV`，该版识别未通过。
- `M0.67A` 按 LEGO 原始固件时序改为先让 pin 6 浮空并读取 pin 5，再把 pin 6 拉低后读取第二次，最后恢复浮空输入；同时把大型马达低编码器相位窗口扩展为 `100..380 mV`。C 设备 B 口大型马达可静止识别且没有转动，但 A/C 空口 `129/249 mV` 也被误判为大型，因此该窗口已撤销。
- `M0.68A` 在恢复原低相位窗口的基础上增加 pin 5 弱上拉阻抗探测，并通过协议 `1.4` 同时返回 pin 6 浮空、pin 6 拉低、pin 5 弱上拉三组 ADC 数据。弱上拉只作用于编码器输入，结束后恢复无上下拉输入及原测速计数，H 桥全程关闭；本版用于采集空口、大型和中型马达的真实阻抗差异。
- `M0.69A` 使用 M0.68A 实物数据完成低相位判据：只有浮空和 pin 6 拉低值都小于 `300 mV` 时才按弱上拉电压区分空口 `200..350 mV`、中型 `380..500 mV`、大型 `520..650 mV`；保护空白区继续返回未知，避免临界值误判。原高相位窗口和协议 `1.4` 诊断数据保持不变。
- `M0.70A` 在四路输出均为自由滑行且马达静止时，以 100 ms 间隔轮询 A-D 的三阶段阻抗识别，单口最迟约 0.4 秒进入下一轮。拔下马达后该口变为空口并清除速度、角度和圈数显示；从空口插入马达或更换类型时会清零测速基线及累计计数。任何马达控制命令都会先取消后台探测，运行中的编码器引脚不会被切换。
- `M0.71A` 针对 M0.70A 实机发现的空口/大型低相位模拟电压重叠，在 pin 5 弱上拉采样时同时读取该 GPIO 的数字高低状态，并通过协议 `1.5` 的 57 字节回包返回。该版只增加诊断字段，暂不改变分类阈值，用于验证弱上拉数字状态能否区分空口和真实编码器输出。
- `M0.72A` 根据同一台大型马达从 A 移到 D 的受控换口实验，以及 EST 3.0 官方 `ChannelMotorCheck()` 的类别顺序，修正 M0.69A 起反向使用的弱上拉窗口：大型 `250..360 mV`、中型 `380..500 mV`、空口 `520..1000 mV`。高相位窗口、扫描时序、协议 `1.5` 和安全停止逻辑不变。C 设备实机已确认马达稳定识别、拔出清除和重插归零；大型/中型 30% 正反向持续定速均跟踪目标，60% 受控负载测试确认输出会提高到 100% 对抗阻力，并在卸载后恢复基线。当前没有电流式堵转保护。
- `M0.73A` 建立正式 `est_*` C 服务层的第一批契约：公共错误码、端口、停止方式、马达/传感器类型，以及单电机和底盘头文件。`est_motor.c` 已适配功率、持续定速、相对角度、停止、全部停止、角度清零、类型和状态查询；现有 HID 电机命令改经服务层但保持原协议。C 设备实机已通过 10% 点动、D 中型 `+60°` 零误差到位和 C 大型 30% 定速回归。按时间运行、位置保持和双电机同步仍明确为未支持。
- `M0.74A` 将速度和位置闭环状态扩展为 A-D 每端口独立实例。新的逐端口快照、停止和更新路径允许一路电机持续闭环时操作另一路；同一端口内的开环、定速和位置命令仍互斥，升级与急停仍关闭全部输出。C 设备已通过 C/D 并发定速、独立停止和并发相反角度到位，测试后四路均恢复功率 0 的自由滑行。
- `M0.89A` 将 UC1638 屏幕的上电空闲、复位保持、复位释放和控制器稳定等待时间放宽为 `50/30/250/100 ms`。一台运行 M0.88A 时只有背光、完全断电后仍无文字的主机升级后恢复正常显示；LCD 接线、控制命令、USB 协议及其他硬件驱动均未改变。
- `M0.90A` 新增 `est_drive_steer_for()`、HID `0x22` 和电脑端 `drive-steer-for`，可沿用 EV3 转向值与有符号速度，按外侧轮圈数、角度或固件内部计时自动完成并停止。原有 `0x21` 持续转向格式和行为保持不变；本版已通过自动测试与构建，等待锂电池条件下实机验收。
- `M0.91A` 新增正式 `est_sensor.h/.c` 服务层，把传感器类型、状态、模式、数值格式、模式切换和端口重启统一为后续 MicroPython 与新上位机可共用的 C 接口。现有 `0x18` 传感器命令和 `0x19` 整机快照已改经该接口，原始类型、数值、诊断字段、USB 帧和协议版本 `1.13` 均保持不变。
- `M0.92A` 新增 `est_display.h/.c`、`est_buttons.h/.c`、`est_led.h/.c` 和 `est_backlight.h/.c`。这些公共接口包装现有已验证硬件驱动，供后续 MicroPython 与新上位机共用；屏幕支持清屏、像素、直线、矩形、英文文字、1 位位图和整帧刷新，按键支持当前状态及按下/松开/长按事件。开机版本画面已改经新屏幕接口，USB 帧和协议 `1.13` 不变。
- `M0.93A` 新增 `est_battery.h/.c` 和 `est_system.h/.c`。电池接口统一返回原始采样、电量档位、百分比和低电量状态；系统接口统一初始化、毫秒时基、紧急停止、退出清理和关机。现有电池门限、PF3 采样、USB 状态帧、升级流程和协议 `1.13` 不变；未经旧引导验证的软件重启明确返回不支持。
- `motor-tacho-test` 支持 1%-100% 可调功率。80% 及以上使用短测试时序：正转 500 ms、关闭驱动 800 ms、反转 500 ms、再次关闭驱动，以降低高速直接换向的冲击。
- `motor-stop-compare` 以默认 60% 功率分别测试旧固件留下的两种合法停车电平组合，通过停车后继续产生的测速脉冲量，实机辨认自由滑行和主动刹车。每项只驱动 600 ms、测量 1500 ms，结束和异常退出均恢复到已经验证过的低电平开漏停止状态。
- 按 1024 字节 HID report 接收升级逻辑帧，同时允许协议层分片输入；逐帧校验、连续性检查、重复上一帧 ACK 和 400 秒会话超时。
- 半帧中断后，如果主机停顿并从新帧头重发，接收器会自动丢弃残帧；设备回包使用 4 项 FIFO，避免前一 ACK 尚在 USB 总线上时丢掉重发响应。
- 首帧确认 `APP=` 后擦除 Sector 8-11，写入完成后检查 MSP 和 Thumb Reset_Handler。
- 最后擦除 Sector 3，按旧语义写入 `package_length - 1`，最后写升级状态 `0x0000`；最终 ACK 发出后拉低 `PE2/PB_CON` 关机，等待人工重新开机。这与 EST 3.0 官方 APP 行为一致，不使用未经验证的软件复位路径。
- 打包器把最终升级文件填充为固定 256 KiB，满足旧 Bootloader 的长度限制。
- 每次构建自动检查 APP 地址、向量表、入口第一条关中断指令、USB VID/PID、1024 字节端点、HS HID/Qualifier 描述符、产品字符串、版本文本、`APP=` 包头、填充内容和 SHA-256 清单。
- `make test` 还会读取 V5.0 当前引脚表，检查电源、LED、六个按键、LCD、背光、音频、外部 Flash、马达、四个输入口和 USB 的代码接线，并拒绝任何重复占用或与原理图不一致的修改。

## 构建

工程内已固定包含 libopencm3 commit `2da12dc96e0b9e42a3332348dd9b02a0a17981f8`。Windows 当前机器可执行：

```powershell
$env:PATH='D:\AIMODU~1\AI_MOD~1\ARM_GC~1\bin;E:\Git\usr\bin;' + $env:PATH
& 'D:\AIMODU~1\AI_MOD~1\make.exe' -j4 all
```

生成 v1/v2 自升级验收包：

```powershell
& 'D:\AIMODU~1\AI_MOD~1\make.exe' -j4 verification-pair
```

`all` 和 `verification-pair` 都会自动执行产物检查。也可以单独执行 `make verify` 复查当前构建目录。

当前项目位于含中文的同步盘路径时，不要使用 `make -B` 强制重建 `libopencm3` 的生成头文件；旧 Windows Make 会在 `GENHDR` 步骤返回 Error 49。正常增量构建会使用仓库内固定版本的既有库。全量重建第三方库时，应先把仓库克隆到不含中文和空格的短路径。

主要产物：

| 文件 | 用途 |
| --- | --- |
| `build/est_minimal_upgrade_app.bin` | 原始 APP，仅供调试器写到 `0x08010000` |
| `build/est_minimal_upgrade_app.app.bin` | `APP=` + 原始 APP，未填充参考包 |
| `build/est_minimal_upgrade_app.upgrade.bin` | 256 KiB，交给旧上位机升级工具 |
| `build/est_minimal_upgrade_app.manifest.json` | 地址、长度和 SHA-256 检查信息 |

不要把原始 `.bin` 交给旧升级工具；应选择 `.upgrade.bin`。该文件已经带 `APP=`，如果旧工具仍会自动添加文件头，需要先确认它的 `Firmware_check()` 不会重复添加。原工具识别到已有 `APP=` 时不会再添加。

## 实机验收顺序

1. 按住第一个按键开机，让板卡进入 Bootloader 下载界面；当前实物表现为红灯闪烁，心跳为 `03.00B`。
2. 使用 `tools/est_hid_sender/est_hid_sender.py` 发送 `.upgrade.bin`。
3. 确认传输完成、Bootloader 搬运后红/蓝诊断灯交替闪烁。
4. 确认 Windows 重新枚举 `VID_0483&PID_5750`，HID 输入/输出报告长度为 `1025`。
5. 确认心跳返回当前六字节构建版本。
6. 生成仅改变版本号的下一版并从最小 APP 再升级一次，验证完整闭环。

只有第 6 步完成，才能说明“新 APP 接收升级包 -> 原 Bootloader 搬运 -> 新 APP 再启动”的闭环真正成立。当前源码和本机测试不能替代实机验证。

当前实物的 Bootloader 在搬运进度达到 `100%` 后不会自动清屏或重新开机；灯熄灭后需要人工断电重启。M0.40A 的屏幕版本显示、蓝灯闪烁和 USB 心跳均正常。M0.39A 在正常开机状态直接接收 M0.40A 的 260 帧，最终 ACK 后约 1 秒内自动关机，确认日常升级不需要预先进入旧引导；只有直接把包发给旧引导时才不会经过 APP 自动关机流程。A 口 30% 测速实测为 `+165/-168`，100% 为 `+421/-375`；A 口自由滑行/主动刹车为 `296/39`。B 口 30% 测速为 `+163/-168`，自由滑行/主动刹车为 `323/37`。M0.38A 的 A/B 同步测试为 A `+162/-172`、B `+178/-178`，实物确认两口同时动作并停止。M0.39A 的 C 口中型马达两次 30% 测速约为 `+108/-303`、`+110/-322`，肉眼正反转速度相同；把同一马达换到已验证 A 口后仍为 `+134/-293`，因此该不对称来自马达个体或中型马达编码器特性，而不是 C 口接线。M0.40A 的 D 口首次测试仅 `+3/0`，重新确认插接后连续两次为 `+143/-246`、`+156/-243`，肉眼确认两个方向均动作并正常停止，因此 D 口驱动和测速已通过。M0.43A 通用控制下 A 口 `+30/-30` 为 `+244/-258`，D 口 `+30/-30` 为 `+215/-369`；A `+30` 与 D `-30` 同时运行时分别为 `+246/-437`。D 口 80% 停车对比为自由滑行后续 `136`、主动刹车后续 `13`，差异明确。M0.44A-M0.51A 已完成现有输入传感器实测，M0.52A 已完成整机状态读取，M0.54A 已确认电池和背光；当前实机测试版本为 `M0.56A`，但音频播放仍未通过。此前 `M0.31A` 的 W25Q256 高地址临时写入、读回、擦除及模式恢复也已验证成功。
