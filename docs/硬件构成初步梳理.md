## 3. 主控型号与启动地址

Keil 工程中存在多个历史 target，例如 STM32F107、STM32F407 等。当前产品主控 APP target 以 `Dr_luck_Robot` 为准。

已确认：

- Keil target：`Dr_luck_Robot`
- MCU：`STM32F429ZG`
- APP 起始地址：`0x0800C000`
- APP 空间大小：`0x74000`
- APP 代码中设置中断向量偏移：`NVIC_SetVectorTable(NVIC_VectTab_FLASH, 0xC000)`

重构新 APP 时，链接地址不能按普通 STM32 工程默认的 `0x08000000`，必须链接到 `0x0800C000`。

## 4. 内部 Flash 分区和升级链路

目前看到的内部 Flash 关键区域：

| 名称 | 地址 | 作用 |
| --- | --- | --- |
| Bootloader 区 | `0x08000000` 起 | 原有底层，不建议改动 |
| 标志/长度区 | `0x08008000` 附近 | 存放升级长度和 APP 配置标志 |
| APP 区 | `0x0800C000` 起 | 实际运行的下位机 APP |
| Update 区 | `0x08080000` 起 | APP 接收新固件后暂存的位置 |

APP 侧地址：

- `APPLICATION_ADDRESS = 0x0800C000`
- `UPDATE_ADDRESS = 0x08080000`
- `Update_Data_Length_L16 = 0x08008000`
- `Update_Data_Length_H16 = 0x08008008`
- `APP_CONFIG_ADDR = 0x08008010`
- `APP_CONFIG_SET_VALUE = 0x5555`

Bootloader 侧地址：

- `APPLICATION_ADDRESS = 0x0800C000`
- `UPDATE_ADDRESS = 0x08080003`

注意：Bootloader 的 `UPDATE_ADDRESS` 是 `0x08080003`。结合旧 APP 写入格式和实际 `_new.bin` 文件头，这个值用于跳过固件文件头 `EST`，从 `0x08080003` 开始搬运真正的向量表和程序内容。这里依赖奇地址半字读取，属于原 Bootloader 的既有行为，重构时不建议改动。

## 5. 固件升级机制

旧工具烧录 `.bin` 时，不是把文件直接交给 Bootloader。流程是：

1. 运行中的旧 APP 通过 USB HID 收到上位机发来的固件帧。
2. APP 将固件数据写入内部 Flash 的 Update 区，也就是 `0x08080000` 起。
3. APP 在 `0x08008000` 附近写入更新长度和配置标志。
4. APP 调用系统复位。
5. Bootloader 启动后检测到更新标志。
6. Bootloader 擦除 APP 区，从 Update 区搬运数据到 `0x0800C000`。
7. Bootloader 清标志，然后跳转到新 APP。

这意味着：如果板子上只有 Bootloader，没有一个兼容旧协议的 APP 接收器，那么旧 HID 烧录工具无法直接发送新 APP 给 Bootloader。解决方向有三个：

- 第一次用 ST-Link/ISP 烧入一个兼容接收器 APP。
- 在新 APP 中长期保留兼容升级接收协议。
- 后续若要完全改变升级方式，必须重新设计并烧写 Bootloader，但这不符合当前“不动底层”的边界。

## 6. USB HID 升级协议

USB 设备信息：

- VID：`0x0483`
- PID：`0x5750`
- 产品字符串：`EST`
- HID 输入包：64 字节
- HID 输出包：64 字节

固件发送帧：

```text
68 11 05 LL HH TT TT II II [payload <= 1010] CS 16
```

字段含义：

- `68`：帧头
- `11`：主机发往设备
- `05`：固件升级功能号
- `LL HH`：数据长度，小端，长度 = `4 + payload`
- `TT TT`：总帧数，小端
- `II II`：当前帧编号，小端，从 0 开始
- `payload`：固件数据
- `CS`：前面所有字节的 8 位累加和
- `16`：帧尾

设备应答帧：

```text
68 21 05 05 00 TT TT II II FF CS 16
```

字段含义：

- `21`：设备发往主机
- `05`：固件升级功能号
- `05 00`：数据长度
- `TT TT`：总帧数，小端
- `II II`：当前帧编号，小端
- `FF`：结果，`01` 成功，`00` 失败，旧源码中超时会用 `02`
- `CS`：前面所有字节的 8 位累加和
- `16`：帧尾

固件文件要求：

- 文件开头必须带 ASCII `EST`。
- 实际资料中的 `Dr.luck_Robot_new.bin` 开头为 `45 53 54`，后面紧跟真正固件的向量表。
- APP 接收端会把包含 `EST` 的内容写到 `0x08080000`。
- Bootloader 搬运时从 `0x08080003` 开始，跳过 `EST`，把后续真正固件内容复制到 `0x0800C000`。

新固件生成要求：

- `.bin` 内部的向量表必须按 `0x0800C000` 链接。
- 用旧协议发送时，传输文件应带 `EST` 前缀，或由发送工具生成这种 `_new.bin` 格式。
- 新 APP 内仍需提供 USB HID 接收和 IAP 标志写入逻辑，否则下一次就无法通过原链路升级。

## 17. 当前最重要结论

新固件不能直接按普通 STM32 程序烧到 `0x08000000`。它必须：

- 链接到 `0x0800C000`。
- 通过兼容 USB HID 协议传输。
- 传输文件带 `EST` 前缀。
- 由运行中的 APP 写入 Update 区。
- 复位后交给原 Bootloader 搬运。

因此，重构项目的第一块新代码不应该马上做完整功能，而应该先做“最小可升级 APP”。只要这个最小 APP 能被旧机制升级，后续驱动重构才有可靠回退通道。
