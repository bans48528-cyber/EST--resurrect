# M1.23C 音频解码诊断候选

## 范围

承接 M1.23B 用户反馈：节奏有响应但声音为同调杂音。该问题尚未验收修复。
本轮不修改 Studio、协议、能力位或电机控制；保留所有原有未提交成果和此前升级包，不提交、推送 Git。

## 修改

- 共享 SPI3 切换/释放片选前，有限等待 TXE 且 BSY 清除。原代码只等待 RXNE，然后立即切换总线。
- 等待失败进入错误清理，复位解码器，不允许永久阻塞。
- 私有音频诊断增加播放载荷 CRC32、DREQ 等待次数和只读 SCI 寄存器访问。
- CRC 只统计实际发送的 MP3 载荷，不含末尾填充；不能证明解码器接收字节正确，需结合 HDAT 和听感。
- 保持原 PG4/PG5/PG6/PG7 配置和 SPI 模式；本轮未尝试交换硬件引脚。

这项总线时序缺陷有源码依据，但尚不能认定它就是杂音根因。
官方依据：VS1003 数据手册 7.3、7.4.2、8.6.9；本地 libopencm3 的 spi_clean_disable 也要求等到 TXE/BSY 完成。
参考：https://www.vlsi.fi/fileadmin/datasheets/vs1003.pdf

## 真机检查

开机后运行 `tools/est_hid_sender/examples/m123c_audio_decode_diagnostic.py`，静音且不运行马达。
结果整数的百万位之前为标志组合：1=读到正确 CLOCKF，2=见到有效 MP3 HDAT，4=见到 22050Hz，8=读到静音音量；其余六位是 DREQ 等待次数。

### 已执行结果

已自动检测到 M1.23C 开机；静音脚本完成，结果 0，未观察到正确时钟、MP3 头、22050Hz 或静音寄存器。
追加 `python -m tools.est_hid_sender.audio_diagnostics` 三轮静音检查，重复得到：

| 项目 | 读回值 |
| --- | --- |
| SCI_MODE | 0x0800 |
| SCI_STATUS | 0x0030 |
| SCI_CLOCKF（发送后） | 0x0000 |
| SCI_AUDATA | 8000 |
| SCI_HDAT1 | 0x0000，无有效 MP3 |
| SCI_VOL（发送后） | 0x0000 |
| 300 ms 内已发送字节 | 8414 = 6366 + 2048 |
| DREQ 等待次数 | 0 |
| 载荷 CRC32 低 31 位 | 1459300450 |
| SDI 结束后重新设静音 | SCI_VOL=0xFEFE，写入能保持 |

最后的发送前后对照返回 15，证实：第一块音频数据发送前 CLOCKF=0x9800、VOL=0xFEFE；发送后两者均变回 0。
这说明 SCI 寄存器读写可用，数据发送伴随复位状态，不能归因于资源本身没有不同音高。
修正 BSY 等待没有解决该现象，未继续播放有声旋律。

当前音频引脚配置和 V5 原理图/用户补充信息一致：PG5=DREQ、PG6=RESET、PG7=XDCS。
但 2018 旧源码为 PG6=DREQ、PG7=RESET、PG5=XDCS，且其 VS1003 与实机 STATUS=0x0030 一致。
现象高度怀疑实机与 V5 图的音频接线版本不同，PG7 数据片选实际触发了 RESET。
这仍是基于行为的推断，未测量实机连线；没有擅自切换到旧引脚或覆盖当前硬件资料。
后续须先核对实机引脚，可采用高阻输入/弱上下拉的安全诊断，不应盲目互换输出引脚。

所有静音检查正常结束，最后设备状态 A-D 均 COAST/power 0；本轮没有驱动真实马达。
