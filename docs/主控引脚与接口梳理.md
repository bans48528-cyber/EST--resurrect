## 1. 最重要结论

- 升级底层 Bootloader 暂不改，新 APP 必须继续兼容旧升级链路。
- 实物 MCU 已确认为 `STM32F429ZGT6`，内部 Flash 为 1 MB；原理图中的 `STM32F407ZET6` 器件字段按历史遗留错误处理。
- 当前协议必须以 EST 3.0 的 `03.00B` Bootloader 和配套 APP 为准。
- 当前 APP 从 USB HID 收升级包，写到内部 Flash 的 Update 区，再设置长度和升级标志并复位，由 Bootloader 搬运到 APP 区。
- APP 链接地址为 `0x08010000`，中断向量偏移为 `0x10000`；`0x0800C000` 是升级长度元数据地址。
- Update 区从 `0x08080000` 开始；文件头为 ASCII `APP=`，Bootloader 从 `0x08080004` 开始读取真正的 APP 数据。
- 最新原理图/BOM 明确出现以下主控硬件：STM32 LQFP144、W25Q64（BOM 标注）、UC1638 LCD、VS1053B、USB3300、LB1836M、HC-05/BLE 接口、USB Mini-B、USB-A Host、4 路输入端口、4 路输出电机端口。实物读取结果确认外部 Flash 实际为 W25Q256JV。

## 3. 升级相关接口

本项目采用的升级版本链路：

| 组成 | 版本/目录 |
| --- | --- |
| 板内 Bootloader | `H:\EST第二期\EST 3.0\EST Bootloader_20180517`，心跳 `03.00B` |
| 当前配套 APP | `H:\EST第二期\EST 3.0\EST Main_20190621` |
| 当前发送工具 | `tools\est_hid_sender\est_hid_sender.py` |

USB Device HID 描述：

| 项 | 值 |
| --- | --- |
| VID | `0x0483` |
| PID | `0x5750` |
| 控制器/PHY | `USB OTG HS` + `USB3300 ULPI` |
| 产品字符串 | `EST USB HS Mode` |
| HID IN Endpoint | `0x82`，1024 字节 |
| HID OUT Endpoint | `0x01`，1024 字节 |
| Report Descriptor | 35 字节，Vendor Defined Usage Page `0x8C` |
| Report ID | 协议内无业务 Report ID；Windows HID API 的 1025 字节缓冲区第 0 字节固定为 `0` |

上位机发出的逻辑帧如下，每帧固件内容最多 1010 字节：

```text
68 11 05 LL HH TT TT II II [payload <= 1010] CS 16
```

设备 ACK：

```text
68 21 05 05 00 TT TT II II FLAG CS 16
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `LL HH` | 数据域长度，小端，等于 `payload长度 + 4` |
| `TT TT` | 总帧数，小端 |
| `II II` | 当前帧号，小端，从 0 开始 |
| `CS` | 从帧头 `0x68` 到 payload 末尾的 8 位累加和 |
| `FLAG` | `0x01` 成功、`0x00` 失败；旧实现还可能用 `0x02` 表示超时 |

当前 EST 3.0 高速 HID 使用 1024 字节 report，一个最大逻辑帧可放入一份 OUT report。Windows HID API 使用 1025 字节缓冲区，第 0 字节为 `0`，后 1024 字节才是协议内容。最小 APP 的协议重组器仍允许分片输入，以兼容诊断和异常重发场景。

当前升级包格式：

```text
ASCII "APP=" + 原始 APP bin
```

没有旧 2018-02-07 链路中的 `EST` 三字节头，也没有文件尾累加校验字节。每个传输帧自身仍有 `CS` 校验。旧 C# 工具的 `Firmware_check()` 会在原始 bin 前自动补 `41 50 50 3D`。

内部 Flash 布局：

| 地址 | 用途 |
| --- | --- |
| `0x08000000` | Bootloader |
| `0x0800C000` | 升级长度低位元数据 |
| `0x0800C008` | 升级长度高位元数据 |
| `0x0800C010` | APP/升级状态标志 |
| `0x08010000` | APP 向量表和代码起点 |
| `0x08080000` | Update 包起点，保存 `APP=` |
| `0x08080004` | Bootloader 实际开始读取的新 APP 向量表 |

APP 区容量为：

```text
0x08080000 - 0x08010000 = 0x70000 = 458752 字节
```

当前 Bootloader 还额外要求元数据中的升级长度严格大于 200 KiB、严格小于 475136 字节。由于 APP 到 Update 边界的实际容量是 458752 字节，发布包还必须满足更严格的 APP 区容量限制。最小 APP 发布脚本把升级包用 `0xFF` 填充到固定 256 KiB，并复现 `接收总字节数 - 1` 的旧长度语义。

新 APP 要保留的最小升级能力：

- USB HID 枚举保持 VID/PID/产品字符串兼容。
- 安全拼接跨多个 HID report 的逻辑帧，并检查帧长、帧号、总帧数和累加和。
- 接收当前帧格式并逐帧 ACK，正确处理重复帧和超时。
- 只在首帧确认 `APP=` 后擦除 Sector 8-11，并把完整升级包写入 Update 区。
- 完整接收后再写入长度和升级标志，不能在中途留下有效升级元数据。
- 复位交给 Bootloader 搬运。
- 构建后自动生成原始 `app.bin`、`APP= + app.bin` 和满足旧 Bootloader 长度限制的填充升级包。

## 4. MCU 主要引脚

当前唯一机器可读引脚表为 `references/hardware/current/EST_MainControl_V5_pin_map.csv`。它按 LQFP144 的 1–144 脚逐项记录当前网络、所属模块和验证状态，共包含 144 个封装脚和 112 个 GPIO。

固件的 `make test` 会读取该表并检查当前使用的电源、红蓝灯、六个按键、LCD 和 USB 引脚；引脚重复占用、代码与表格不一致或再次出现 `PB13/LCD_SCK` 冲突都会导致测试失败。

旧版 `LEGO_1220` 引脚表及旧映射不再出现在活动文档中，只保存在 `references/hardware/legacy/` 用于追溯。

## 13. 当前待确认清单

MCU 型号和 Flash 容量问题已经解除：实物为 `STM32F429ZGT6`，按 1 MB 内部 Flash、APP 起点 `0x08010000`、Update 起点 `0x08080000` 开发。

板上心跳 `03.00B` 已与 EST 3.0 Bootloader 对上。当前仍需通过实机闭环确认两个高风险项：

1. `M0.11A` 能否接管 HS ULPI HID 并返回版本心跳。
2. `PE2/PB_CON` 高电平是否能在 Bootloader 跳转后持续保持板卡电源。

工程实现中必须处理的已知问题：

- Bootloader 跳转 APP 不是硬件复位。它在跳转前初始化过时钟、LCD、W25Q、SPI3/VS1053、DMA、定时器和多组 GPIO。APP 入口应立即关中断，停止 SysTick，清 NVIC enable/pending，停止遗留外设，设置 `SCB->VTOR = 0x08010000`，再完整重建系统时钟和 HS ULPI USB。
- Bootloader 只接受 `> 200 KiB` 且 `< 475136` 字节的升级长度，最小 APP 的升级包必须填充，建议固定为 256 KiB。
- Bootloader 搬运代码把 `u16` 数量和字节地址步进混用，并使用 `i <= Buff_Num`，会重叠搬运并越过真实长度。第一版不修改 Bootloader，只保证有效固件前缀、尾部 `0xFF` 填充和偶数字节长度与现有行为兼容。
- Bootloader 跳转前的 MSP 合法性检查被注释，且没有完整固件 CRC 或签名。新 APP 至少要在设置升级元数据前校验包头、向量表范围、每帧校验和、帧连续性和最终长度。
- 若候选 APP 的 USB 或电源保持失败，需要重新进入板载 Bootloader 下载界面再发送恢复包或下一候选包。

这些问题不阻塞最小可升级 APP，但后续仍需确认：

- 功放实物型号：`PAM8301` 还是 `NS4150`。
- LCD 背光网络已由 V5.0 图面确认为 `PA8`；当前固件保持 Bootloader 留下的背光状态，后续再决定是否主动控制。
- USB-A Host 口是否为后续功能必须项，若新 APP 暂不实现，可先不影响固件升级。
- 4 路输入端口的 `TXINx_EN` 和 `RXINx_EN` 在 74HC125/电平转换中的确切方向，需要打开 AD 或实测。

## 14. 重构建议顺序

1. 让板卡进入 `03.00B` Bootloader 下载界面，使用当前 HID sender 发送已验证的 `M0.11A`。
2. 验证高低电平保持、诊断 LED、HS HID 重新枚举和 `M0.11A` 心跳。
3. 做只改变版本标识的下一版，由 `M0.11A` 自身接收并升级。第二次升级成功才证明重构后的 APP 真正保住了升级链路。
5. 补测断线、重复帧、乱序帧、错误校验、错误包头、奇数原始长度、边界长度和接收中断电。
6. 再做基础板级驱动：时钟、GPIO、电源保持、LED、按键、LCD。
7. 然后做外设驱动：W25Q256JV、VS1053B、蓝牙、USB Host。
8. 最后做业务端口：4 路输入传感器、4 路电机输出、测速/电流检测。

最小 APP 的验收标准不是“v1 能通过旧工具烧进去”，而是“v1 能稳定接收 v2，并由原 Bootloader 成功搬运后启动 v2”。
