最后更新：2026-09-01

## 1. 唯一目标

1. 参考 Pybricks 的公开架构和语义，提高 EST 程序运行效率、响应速度和长期可维护性。
2. 实现当前 EST Studio 对应的全部 EV3 Classroom 积木功能；只有经代码、原理图或真机证明 EST 硬件确实无法实现时，才能记录为硬件限制。
3. 所有积木始终在 Studio 中显示。暂未实现的积木必须明确标记并在下载前说明原因，不能隐藏、删除或运行后只报 `E3`。

Pybricks 仅作为设计参考。不得直接复制其源码，也不能为了形式一致而加入 EST 硬件不具备的虚假能力。

## 2. 本文档的维护规则

- 本文档是后续上下位机工作的唯一总清单；旧分析文档保留为历史证据。
- 由本协调对话维护本文档。上位机和下位机任务只提交结果，不同时编辑本文档，避免冲突。
- 每次发出任务提示词前，把对应任务改为“进行中”。
- 每次收到任务结果后，记录修改文件、测试、候选版本、真机结果和遗留问题，再决定下一项。
- “代码已写”不等于完成。完成必须同时满足：生成正确、下位机运行正确、安全停止正确、自动测试通过、真机验收通过。
- 未经用户明确要求，不提交或推送 Git；首次升级任何候选固件前必须等待用户确认。

状态只使用：`待开始`、`进行中`、`待真机`、`已完成`、`硬件限制`、`阻塞`。

## 4. Pybricks 参考后冻结的设计方向

| Pybricks 公开方向 | EST 采用方式 |
| --- | --- |
| 普通积木尽量直接生成可读的对象/API调用 | Studio 不再注入大段通用 helper；参数规范化集中到 runtime/原生层 |
| 用户设备 API 主要由固件中的 C 模块提供 | EST 的硬件、状态机和高频路径放在 C 层；`est_runtime.py` 保留薄兼容层 |
| 只有多任务或多个开始入口才增加 async 调度代码 | 单程序堆保持简单；多开始帽、事件和等待才进入协作调度器 |
| 有限动作支持等待和非等待，运行状态可查询 | EST 统一 `wait/done/state/stalled` 语义，不用 Python 延时模拟 C 层动作 |
| 新的 Motor/DriveBase 命令会接管资源并取消旧动作 | EST 继续使用 owner/generation，并覆盖所有积木电机入口 |
| I/O 与长动作可协作等待，停止路径始终可取消 | 传感器、音频和显示长操作必须保持 USB、Back、STOP、电机 tick 和 watchdog |
| 稳态调度循环避免无意义 GC 和频繁分配 | 先测量，再把高频事件采样和等待状态移入预分配结构或 C 层 |
| 固件使用尺寸优化并已采用 LTO | EST 只在独立构建实验中评估 LTO，必须比较体积、时序和真机稳定性后采用 |

不照搬的内容：毫米 DriveBase、轮径/轮距模型、多组 DriveBase、无法验证的扭矩/负载估算、操作系统线程。

- EST红外事件2个：红外接近、红外信标按钮。
- EV3传感器6个：等待主机按钮、重置反射光校准、等待颜色、等待触碰、等待超声波、等待陀螺仪。
- EST红外传感器8个：等待接近、信标方向、信标距离、信标按钮列表、信标按钮判断、等待信标按钮、信标活动状态、信标属性比较。

另外6个必做声音积木均不可运行：播放并等待、开始播放、有限音调、持续音调、停止声音、设置音量。板层只有 VS1003B 测试 WAV 和音量接口，尚未形成 MicroPython `est.audio` 与资源播放状态机。

这些缺口不能笼统写成“硬件未实现”：双速度底层 MotorPair/C 已存在；红外底层已有频道1的接近度、`beacon()` 和 `remote()` 原始结果；温度摄氏/华氏读取已有完整路径；多数传感器缺口是 runtime 包装、非阻塞采样和事件状态。

### 5.4 主机按钮差异

EV3截图中有3个默认选择“中”键的积木：按钮事件、等待按钮、按钮是否按下；另有1个“按钮”值积木。EST没有独立中键，物理键为返回、左、上、下、右、确认；源码中的 `CENTER` 只是 `CONFIRM` 的兼容别名。

本项目采用以下诚实适配：

- 四类按钮积木全部保留，不显示或宣称 EST 有“中键”。
- EST工程使用实际按钮名称，EV3旧工程的“中”明确迁移为“EST确认键（兼容EV3中键）”。
- 返回键是全局安全停止键，不能作为普通事件/等待键提供虚假的可达语义。
- 当前 `sensor_brick_button_value` 直接返回按键位掩码，不等于 EV3 的单按钮编号；必须在按钮/广播批次中冻结编号、多键和无键语义。

### 5.5 已知硬件差异

| 功能 | 结论 | Studio处理 |
| --- | --- | --- |
| 红外频道2～4 | 当前 EST 外设只实际提供频道1 | 新工程只提供频道1；旧工程2～4明确提示后迁移为1 |

## 6. 运行效率现状与测量要求

已具备的基础：

- 电机闭环、轨迹和硬件 tick 在 C 层运行。
- 主服务以1 ms时间基更新，VM hook维持 USB、运行时服务、STOP和watchdog。
- frozen runtime 已缓存 Motor、DriveBase 和传感器对象。
- Studio 2.8.1 已移除速度 helper 生成膨胀，连续电机入口已统一进入 runtime owner/generation。

当前主要效率风险：

1. 传感器构造、首次读取或模式切换可在一个 Python 调用内同步等待最多约3秒；硬件仍运行，但其他 Python任务不能前进。
2. Python协作调度器每轮遍历任务和事件；新增传感器事件前必须避免稳态分配和重复切换模式。
3. 高层 runtime 仍是纯 Python；热点尚未用数据证明哪些值得下沉 C 层。
4. 每次运行都解析和编译源码；源码上限8 KiB，尚无真实大型积木项目基准。
5. `print()` 被丢弃，异常只形成 E3，性能问题和错误位置难以定位。
6. 当前只记录启动、堆和最大 GC 停顿，没有事件延迟、调度吞吐、传感器新鲜帧延迟和上传耗时基线。

每一批后续修改都必须记录修改前后至少以下指标中的相关项：

- 生成 Python 字节数。
- 程序上传与开始执行耗时。
- VM 启动时间、剩余堆、最大 GC 停顿。
- 单/多程序堆调度循环和事件触发延迟。
- 传感器首次读取、同模式读取、切换模式耗时。
- 电机命令接管、STOP和异常清理延迟。
- LCD刷新和音频数据发送期间的最大 runtime tick 间隔。
- 固件原始体积和固定升级包剩余空间。

不同 MCU 的绝对跑分不能直接与 Pybricks 比较。优化结论必须来自 EST 同一台设备修改前后的数据。

## 8. 每一批的固定执行顺序

涉及下位机能力时严格按以下顺序：
