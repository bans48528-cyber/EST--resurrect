## 两个独立问题

1. 测试脚本使用 `enumerate()`，当前 MicroPython 最小配置未启用该内置函数。
   最初程序约 1340 ms 异常，结果值未设置，尚未进入第一音符的循环体。
   已改为普通元组循环与显式计数，不通过扩大固件内置函数范围绕过。
2. 普通循环重测后，前六个 450 ms 音符的等待结束时仍处于启动阶段，
   第七个 900 ms 长音暴露了解码器启动超时。诊断结果 `29000000` 表示
   state=2、phase=9、bytes_sent=0；这不是已发送音频后发生断音。
   目前证据是 DREQ 没有就绪，不能据此宣称芯片损坏，也不能宣称扬声器正常。

`LINE1` 不是真正的异常位置：端口配置使用 ROM_LEVEL_MINIMUM，未显式启用
`MICROPY_ENABLE_SOURCE_LINE`，因此运行时代码缺少精确行号信息。
M1.23B 显式开启源行号记录。屏幕行号仍待实机确认，不修改现有协议载荷。

## M1.23B 改动

- DREQ 输入恢复旧驱动采用的上拉配置。
- 复位低电平保持从 2 ms 延长为 10 ms，原有 500 ms 启动等待仍有限。
- 严格保留 DREQ 门控，不在未就绪时强行发送音频。
- 私有 `_diagnostics()` 增加 PG4～PG7 实际电平和失败前控制阶段。
- 保留 STOP、Back、断线和程序退出时硬件复位音频芯片的清理。
- 开启精确 Python 源行号信息。

VS1003 官方资料说明，复位后需要等待 DREQ 再初始化寄存器并发送数据：
https://www.vlsi.fi/fileadmin/datasheets/vs1003.pdf ，第 7.3、9.2 节。
本次恢复上拉与增加复位保持是板级兼容排查，不是已经证明的硬件根因。
