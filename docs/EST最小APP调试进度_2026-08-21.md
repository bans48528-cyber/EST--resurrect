# EST 3.0 最小 APP 调试进度

更新时间：2026-08-21  
当前阶段：`M0.17A` 冷启动自升级闭环已成功；准备迁移开发环境

## 1. 项目目标与当前工作

本阶段目标是在保留设备原有 EST 3.0 Bootloader 的前提下，重建一个可通过现有 HID 升级链路安装的最小 APP。该 APP 首先需要完成以下闭环：

1. Bootloader 能正确接收升级包、复制到 APP 区并跳转。
2. APP 能维持主板供电并通过板载 LED 给出明确运行状态。
3. APP 能以原设备兼容的 USB HS/ULPI HID 接口重新枚举。
4. APP 能响应心跳，并最终具备接收下一版升级包的能力。

当前工作不包含替换 Bootloader，也不依赖 ST-Link/SWD。官方 APP 恢复包始终保留，未经用户要求不主动发送。

## 5. 已确认的 Bootloader 行为

1. 收到第 0 包并识别 `APP=` 后，Bootloader 会点亮红灯。
2. 第 0 包处理会同步擦除 Flash 扇区 8、9、10、11，随后才返回 ACK。
3. 全部数据接收完成后，Bootloader 写入升级长度和状态，并设置 `app_update_flag`。
4. 定时器约 3 秒后执行 `App_Update_Check()`，将升级区复制到 APP 区。
5. 复制后 Bootloader 停止 USB Device，并直接跳转 APP，不执行硬件复位。
6. 屏幕上的“正在更新 100%”可能继续保留，因为最小 APP 尚未初始化 LCD；该画面不能单独证明 Bootloader 卡死。

因此，升级过程中从 `0%` 开始常亮红灯属于 Bootloader 的正常行为。此前仅凭最终常红判断 APP 已进入 Reset Handler 的结论不可靠，现已由 `M0.14A` 的入口闪灯签名替代。

## 6. 发送器修正

发送器原先对所有数据包统一等待 4 秒。由于第 0 包包含四个大扇区的擦除操作，实机曾在 `1/260` 处误报超时，但设备仍可回应 `03.00B`。

当前规则：

- 第 0 包 ACK 超时：15 秒。
- 其余包 ACK 超时：4 秒。
- 修改后 `M0.12A`、`M0.13A`、`M0.14A` 均完成 `260/260`。

## 9. M0.16A 官方栈指针对照版

官方恢复包向量表：

- 包头：`APP=`
- 初始 MSP：`0x2002D3B0`
- Reset Handler：`0x0801019D`

`M0.16A` 将链接脚本的初始 MSP 调整为同一个 `0x2002D3B0`，以排除 Bootloader 在切换到边界栈 `0x20030000` 后、调用四个反初始化函数期间发生异常的可能性。

升级包：`firmware/minimal_upgrade_app/build/v16_official_stack/est_minimal_upgrade_app.upgrade.bin`

| 校验项 | 值 |
| --- | --- |
| 版本 | `M0.16A` |
| 原始 APP 大小 | 10560 字节 |
| 升级包大小 | 262144 字节 |
| 初始 MSP | `0x2002D3B0` |
| Reset Handler | `0x08010451` |
| SHA-256 | `de70124ae0b3cedbce2610dcfef8fca0af8ec5d398a6ec83942f29a49e102e11` |

### 本次实机结果

1. 发送前 Bootloader 心跳为 `03.00B`，HID 输入和输出 caps 均为 1025。
2. 260 个数据包全部收到成功 ACK。
3. 更新后现场明确观察到红蓝交替着陆信标，证明 APP Reset Handler 已执行。
4. 着陆信标结束后重新建立 HID 通信，设备心跳返回 `M0.16A`。
5. 屏幕仍保留“正在更新 100%”，符合最小 APP 尚未初始化 LCD 的预期，不影响启动成功结论。

结论：`0x20030000` 这一 RAM 边界值是 M0.15A 及此前版本未能进入 Reset Handler 的关键差异。Bootloader 在设置 APP MSP 后、真正调用 Reset Handler 前还会执行若干外设反初始化；使用边界栈可能使这段代码发生异常。将 MSP 调整为官方值 `0x2002D3B0` 后，APP 启动链路和 USB 心跳链路均已打通。

## 10. 现场判断方法

升级进度到 `100%` 后继续观察至少 8 秒：

| 观察结果 | 含义 |
| --- | --- |
| `M0.15A` 在 `100%` 后持续红蓝交替 | Bootloader 已成功复制，并执行到 APP Reset Handler；基础 GPIO 和看门狗喂狗正常 |
| 完全没有出现入口闪灯签名，始终保持 Bootloader 红灯 | APP Reset Handler 未执行，应优先检查复制后的向量表、跳转条件和实际 Flash 内容 |
| 出现入口签名，随后持续红蓝交替 | APP 主循环和 SysTick 正常，剩余问题集中在 USB 心跳链路 |
| 出现入口签名，随后常蓝 | 卡在外设准备或 USB 初始化检查点 |
| 出现入口签名，随后红蓝同时常亮 | USB 初始化已返回，但中断或主循环没有正常推进 |
| 出现入口签名，随后常红 | 进入了 APP，但停在较早的协议初始化检查点或发生复位循环 |

## 13. `est V1.0 Chinese` 历史资料评估

已检查 `est V1.0 Chinese/技术文档.zip`、`EST项目测试报告.xlsx` 以及三份旧版 Qt 上位机源码目录。

有价值的内容来自 2016 年《乐博士可视化编程机器人上下位机通信协议》：旧协议同样使用 `0x68` 帧头、`0x11/0x21` 方向码、`0x05` 固件下载功能码、总包数/当前包序号和逐包 ACK；最后一包成功后未定义额外的复位或重启命令。这支持当前发送器的基本帧结构，也说明“更新 100% 后停留”不能简单归因于漏发一条复位指令。

资料限制：

- 文档面向第一代协议和旧版全速 HID，报告长度为 64 字节。
- 未发现 EST 3.0 的 APP 地址、升级区地址、元数据地址、向量表或 Bootloader 跳转实现。
- 《升级模块说明》描述的是 PC 软件通过 FTP 自更新，与主控固件升级无关。
- 测试报告主要记录 2018 年上位机和应用固件功能问题，未记录固件升级后的自动重启时序。
- Qt 源码中未发现 Bootloader、固件打包或固件升级发送实现。

因此该资料只作为历史协议旁证，不能覆盖 EST 3.0 官方源码所确定的当前参数。首次准备发送 `M0.16A` 时，Windows 曾短暂未枚举到 `VID_0483&PID_5750`；设备重新进入升级模式后发送成功，最终结果见第 9 节。

## 14. M0.17A 短启动签名与首次自升级闭环

升级包：`firmware/minimal_upgrade_app/build/v17_short_start/est_minimal_upgrade_app.upgrade.bin`

| 校验项 | 值 |
| --- | --- |
| 版本 | `M0.17A` |
| 原始 APP 大小 | 10560 字节 |
| 升级包大小 | 262144 字节 |
| 初始 MSP | `0x2002D3B0` |
| Reset Handler | `0x0801044D` |
| SHA-256 | `e88306c61a10588d2d2dbee682980f6843e0494de5baa5a622991ed14ac2bd77` |

构建验证、9 项单元测试和反汇编检查全部通过。反汇编确认入口信标循环上限为 6 个相位。

本次没有人工切换到 Bootloader：发送前设备心跳为 `M0.16A`，随后由 M0.16A 自身接收 M0.17A，260 个包全部成功 ACK。发送完成后，M0.16A 写入升级元数据并执行软件复位；设备随后红灯常亮，超过两分钟仍未重新枚举 `VID_0483&PID_5750`，M0.17A 入口签名没有出现。

重新核对官方 EST 3.0 APP 的 `Project/src/IAP/iap.c` 后确认：官方 APP 写完升级元数据会等待 1 秒并调用 `Power_Off()`，其 `NVIC_SystemReset()` 调用被注释。也就是说，官方 APP 自升级流程要求先关机，再由用户重新开机触发 Bootloader 搬运；软件复位不是已验证路径。

现场随后彻底断电 2 秒并正常开机，观察到约 2 秒红蓝入口签名，之后转为仅蓝灯慢闪；屏幕不再显示更新画面。主机心跳确认版本为 `M0.17A`。至此，“M0.16A 接收升级包 -> 冷启动 Bootloader 搬运 -> M0.17A 启动 -> USB 心跳恢复”的完整闭环已经实机验证。

仓库源码已在 M0.17A 基础上恢复官方关机语义，下一次构建应使用 `M0.18A`；该源码修正尚未发送到设备。
